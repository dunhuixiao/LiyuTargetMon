# 配置格式与仓库规则

生成条目、写入配置或复核修改时读取。以当前仓库文件为最终依据；下面记录本项目已确认的约定。

草稿收录范围以用户明确点名或确认加入的 Buff／Debuff 清单为准，用户指定加入优先于默认数值筛选阈值。其余条目默认忽略，包括已通过阈值或已核实 BuffID 和 IconID 的条目。

## 文件与同步范围

仓库通常位于 `D:/Code/LiyuTargetMon`，以下路径均相对仓库根目录：

| 文件 | 用途 |
| --- | --- |
| `docs/.vuepress/public/targetmon/prioritylevel/BuffPriorityLevel.jx3dat` | 仅正面 Buff |
| `docs/.vuepress/public/targetmon/prioritylevel/DebuffPriorityLevel.jx3dat` | 仅负面 Debuff |
| `docs/.vuepress/public/targetmon/【鲤鱼监控】v版本号（四行模式）.jx3dat` | TARGET 与 CLIENT_PLAYER 各有正、负面容器 |
| `docs/.vuepress/public/targetmon/prioritylevel/AllBuffPriorityLevel.jx3dat` | 全职业正负状态混合，含独立特殊处理 |
| `docs/.vuepress/public/targetmon/【鲤鱼监控】v版本号（两行模式）.jx3dat` | TARGET 与 CLIENT_PLAYER 各一个混合容器 |

实际版本文件名从目录和用户指令识别；`v版本号` 是此文档的路径说明，不是真实文件名。用户限定某几个文件时按该范围操作；若指令只是承接当前会话，则继承已确定范围，不自行扩展到历史版本。

`AllBuffPriorityLevel` **不能通过 Buff 和 Debuff 简单相加重建**。三份列表的大部分状态相同，但允许有特殊等级、独有条目和不同排序。

在五文件均属于本次范围的常见情况下，按以下顺序核对份数。

- 新增正面状态依次进入 Buff 一处、四行两个 Buff 容器、All 一处、两行两个混合容器。
- 新增负面状态依次进入 Debuff 一处、四行两个 Debuff 容器、All 一处、两行两个混合容器。
- 因此一个新状态通常有六份记录，但这只是核验预期；现有特殊规则或用户限定范围优先，不能为凑数量补入不适用容器。

## 固定操作顺序与对应关系

可以先只读分析全部文件并准备备份，实际修改、保存和同步按以下顺序执行。批量脚本的文件遍历及写入顺序也采用此顺序。

1. 处理 `BuffPriorityLevel.jx3dat` 和 `DebuffPriorityLevel.jx3dat` 中适用的条目，确定各自的类别、门派和段内位置。
2. 根据刚处理的源表操作四行模式，分别同步 TARGET 与 CLIENT_PLAYER 的对应正面或负面容器。
3. 独立处理 `AllBuffPriorityLevel.jx3dat`，按 All 自身的分类、门派顺序及特殊规则确定位置。
4. 根据 All 表操作两行模式，同步 TARGET 与 CLIENT_PLAYER 两个混合容器。

| 源表 | 对应导出文件与容器 |
| --- | --- |
| BuffPriorityLevel | 四行模式的两个 Buff 容器 |
| DebuffPriorityLevel | 四行模式的两个 Debuff 容器 |
| AllBuffPriorityLevel | 两行模式的两个 Buff／Debuff 混合容器 |

修改时覆盖原条目位置。新增时追加到目标类别下目标门派段的最后一条之后、下一个门派注释之前，同批条目的顺序沿用确认后的顺序。源表没有该门派段时，按同类别现有门派顺序建立注释段并插入。删除时定位指定 `dwID + nLevel` 的完整条目，再按上表同步对应导出。

导出文件中的“相同位置”指与对应源表一致的类别、门派和前后条目相对顺序。通过相邻 ID、等级和类别核对位置，文件行号仅用于定位。每组完成后核验源表与对应容器，再进入下一组。

## 分类、顺序、颜色和边框

- 优先级文件按“效果类别 → 门派”组织，门派名在各类别会重复。必须同时定位类别注释和门派注释，再检查下一个门派边界。
- 依据实际效果和相邻同类条目选择“化解／减伤”“定身”“免控”“其他”等类别与 `szContent`。
- “其他”类别中的正面 Buff 和负面 Debuff，默认以状态名称作为显示别名，设置 `szContent = szNote`。即使效果属于叠层或联动标记，也采用此默认值，例如“戎行”显示“戎行”。用户指定或该状态已确认的特殊显示规则可覆盖默认值，“标记”属于这类特殊别名。
- 同类别内按现有门派顺序插入，新增追加到该门派段末尾。完整导出若没有对应注释，四行使用 Buff／Debuff 源表、两行使用 All 源表中的相邻 ID 和等级定位，并分别核对每个容器。
- 正面默认 `aContentColor = {255, 255, 31}`，负面默认 `{255, 31, 31}`。特殊状态以已有同类规则为准；混合 All 内也要保留正负颜色差异。
- 边框由外层容器 `szBoxBgUITex` 管理，不是每条 Buff 的字段。已用配置中四行 Buff 纹理后缀为 `|4`，Debuff 为 `|1`；两行混合为 `|9`。读取当前实际容器确认并原样保留，不把固定后缀硬写到所有文件。

## 心法与 PvP 适用范围

默认处理 DPS、治疗心法及门派通用的 PvP 效果。先按心法筛选，再核对效果作用对象和触发对象。

- T（坦克）心法专属效果默认从技改分析、候选、历史补漏、待截图清单及条目生成范围中过滤。用户明确指定心法范围时采用其要求。
- 同一技能或 BuffID 有多个心法来源时，核实非T心法或门派通用来源是否仍可触发。可触发的分支继续处理，按该分支的效果计算阈值。
- 心法范围用于本轮分析及候选筛选。已有配置的清理按用户指定的具体状态执行。

- 明确仅针对非侠士、NPC、首领或副本战斗的效果，直接过滤。仅通过命中或击杀非侠士目标才能获得的自身增益，同样按此规则过滤。
- 按用户指定的 PvP 筛选规则，奇穴效果明确包含无双或无双等级加成时，将该奇穴及其关联 Buff 效果整项按 PvE 过滤。即使同时提高会心、会效、伤害或提供减伤，也一并筛除。此规则先于强化范围分类、叠层计算和数值阈值判断，适用于效果表、候选、历史补漏、待截图和条目生成。判断依据为实际无双属性加成。
- 莫问混选「师襄」同时提高会心效果和无双等级，整项过滤。会效最高18%仍按上述规则筛除。
- 通过上述筛选后，对同一技能或状态中针对侠士、非侠士的不同分支，提取对侠士有效及通用的部分。后续阈值计算只采用这些部分的数值与层数。
- 涉及宠物、伶影等实体的招式，按实际效果和触发目标判断 PvP 适用性。
- 用户说明、效果表格、待处理清单、补漏候选和待截图清单均仅包含通过 PvP 筛选的项目。原始证据及过滤原因可保留在内部追溯资料中。

## 增伤状态的强化范围

通过 PvP 适用性筛选后，判断实际受益的招式范围，再决定分类和监控价值。

- **爆发用于通用强化**，例如广泛作用于自身输出的攻击、伤害等增益。判断依据是效果的适用范围，触发技能单独记录。
- 单个招式、下一次特定招式施展、限定套路的强化，以及目标只受到指定招式增伤的效果，按特定强化单独评估。结合用户指定、已有规则或实际监控用途，决定个别状态是否归入“其他”，并在分析记录中写明收录理由。
- 强化范围决定分类。百分比和叠层总值用于完成分类后的数值筛选，爆发阈值仅适用于通用强化。
- 同一状态还带有瞬发、免控、减伤等监控功能时，按已确认的功能及用户指定选择类别与别名。“其他”采用上文的别名规则，并保持该状态实际的正负面属性。

无相楼「缭乱」仅强化“傀儡调”套路，属于特定套路强化。「七撩」使目标受到“千里急”伤害提高，属于敌方特定易伤。两项均按上述特定强化规则评估，用户明确指定加入草稿时归入“其他”，七撩使用负面容器和颜色。生发按本会话用户指定归入“其他”，别名“瞬发”。

## 默认候选筛选阈值

分析候选时，先完成 PvP 适用性、强化范围与监控价值判断，再执行以下默认数值筛选。草稿收录以用户明确指定为准。用户明确指定加入的条目，即使低于以下阈值也按指令收录。通过阈值的候选，须经用户明确指定加入后才生成草稿。

| 效果类型 | 筛除条件 |
| --- | --- |
| 减伤 | 该状态可达到的有效总数值小于或等于15% |
| 爆发（通用强化） | 该状态可达到的有效总数值小于或等于15% |
| 化解 | 数值小于10%，且不能叠层 |

减伤和通用爆发可叠层时，记录单层百分比、最大层数及叠加规则，按可达到的有效总效果判断。线性相加时用单层百分比乘最大层数，有乘算规则或上限时按实际规则计算。通用增伤每层8%、最多3层，最高24%，应纳入候选。无尘每层10%、最多3层，最高30%减伤，应纳入。每层5%、最多3层，总计15%则筛除。

上述总效果用于默认候选筛选。显示时的层数条件仍按用户指定或既有规则设置，默认 `nStackNum = 0`。化解效果采用上表的化解阈值，包括放在“减伤”大类里的护盾。化解恰好10%，或数值低于10%但能够叠层时，继续进入候选核验。

数值和游戏实际叠层能力通过截图、实测或对应版本 Buff 数据确认。信息不足时记录待核。候选筛除项在临时分析中记录原因，草稿清单按用户明确指定生成。已存在条目的清理按用户另行给出的删除范围执行。

## 字段约定

- 用 `dwID + nLevel` 识别具体监控条目。**所有新增 Buff／Debuff 的草稿和配置默认使用 `nLevel = 0`，表示不限等级匹配。** 数据库或截图中的实际 `Level` 保存在证据记录中，未知时标记待核。即使截图明确显示 `Level = 1`，配置仍按默认通配规则生成。
- 个别条目确需限定非零等级时，例如同一 BuffID 的不同等级对应不同效果且需要区分监控，先列出名称、BuffID、建议 `nLevel`、限定理由及使用 `0` 会匹配到的相关效果，返回用户确认后采用。用户已经明确指定配置等级时，按该指令处理。其余使用默认等级的条目按已有授权继续处理。
- `nStackNum` 默认 0，`bEnable` 默认 true；如同类配置有特殊值则保留。
- 新状态分配一个大写带连字符 UUID；同一状态在各对应列表中复用它。保留已存在条目的 UUID，重试插入时先查已存在的 ID／等级，不能再生成一份重复项。
- `szNote` 用确认的状态名称，`szContent` 为显示别名，按上述类别规则设置。效果全文、来源技能、证据放在临时分析 JSON 中，不擅自给导入条目添加未知字段。

## 用户要求的输出格式

此项目口头所称“JSON”常指下面的 Lua table 配置片段。保持字段顺序、制表符缩进、颜色多行、尾随逗号。优先级条目通常外层一制表符，完整导出 `aMonitor` 条目通常外层三制表符，以当前位置为准。

以下“戎行”示例演示“其他”类别以状态名称作为别名的格式。ID 和图标来自已核实截图，配置等级按默认规则设为 `0`，UUID 为格式占位值，实际新增时另行生成。

```lua
	{
		szNote = "戎行",
		dwID = 34368,
		nIconID = 28361,
		szUUID = "00000000-0000-4000-8000-000000000000",
		nStackNum = 0,
		nLevel = 0,
		aContentColor = {
			255,
			31,
			31,
		},
		szContent = "戎行",
		bEnable = true,
	},
```

严格 JSON 使用相同字段名，但字符串键加引号、赋值用冒号、颜色用数组，不含注释和尾随逗号。例如 `"aContentColor": [255, 31, 31]`。将配置条目和分析元数据分开，避免把分析对象当作可直接导入的条目。

## 写入与复核

1. 记录当前原始文件内容、编码、换行及 Git 差异。此前 `.jx3dat` 为 GB18030／GBK 兼容字节与 CRLF，日志为 UTF-8；现场检查后按实际编码原样读写，不用默认 UTF-8 覆盖 `.jx3dat`。
2. 将修改前备份放到系统临时目录。已有未提交变更也包含在备份中；不要用 HEAD 恢复整文件覆盖用户工作。
3. 按“Buff／Debuff → 四行 → All → 两行”的顺序编辑已授权条目。Lua table 可能有嵌套颜色等表，删除必须覆盖完整条目，不能用“直到第一个右花括号”为止的简单正则截断。使用结构解析或经过核对的完整片段定位，不执行导出文件里的任意代码。
4. 分别验证 Buff 与四行 Buff 容器、Debuff 与四行 Debuff 容器、All 与两行混合容器。核对本次新增条目均在用户明确指定的清单内。检查条目完整、字段正确、位于对应类别及门派，修改覆盖原位置、新增位于门派段末尾，同一列表无新增重复 ID／等级或 UUID。允许同一 UUID 在不同对应容器复用。
5. 删除条目后复查各授权容器的残留；新增后核对实际份数。比对未触及条目的内容与相对顺序、类别和门派注释、外层边框与其他设置。
6. 检查实际字节与中文解码、CRLF 和 Git 差异。终端显示乱码不等于文件损坏；发现真实损坏时先留备份并确认可恢复范围，不能未经比较就用历史文件覆盖整份配置。

单次校验通过后交付简短操作结果与文件位置；不要重复跑与本次数据变更无关的全项目测试。
