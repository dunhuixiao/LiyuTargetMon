# 剑网三门派 Buff 更新

以 PvP 为主要监控目标，将指定门派的旗舰版技改转为有依据的监控配置操作。默认在用户指定的门派、版本及日期范围内处理非T心法和门派通用效果，过滤 T（坦克）心法专属内容，排除移动端、悟心法、无界和绝境战场。用户明确指定心法范围时按其要求处理。版本、门派、截止日期从当前会话与仓库确认，不固定为纯阳、苍生铸世或某月 29 日。

## 阶段与指令边界

按用户制定的顺序工作；已有材料和已完成阶段可以直接复用：

1. 找到对应门派的技改文档，对照现有配置，找出确定需要新增、修改、删除的状态。
2. 查 Buff 数据库；数据库未更新或无法确认时，利用用户提供的游戏调试截图核对 ID、等级、图标和效果。
3. 对用户明确指定加入草稿的 Buff／Debuff，基于确认的数据生成 JSON／配置条目。**收到插入或修改文件的指令后，才写入仓库配置。**
4. **收到更新日志的指令后，再按仓库历史格式处理目标版本的门派日志。**

“分析技改”“查数据库”按用户请求的研究范围执行。“根据截图生成 JSON”等草稿请求只处理用户明确指定的条目。“直接插入”“把这些加入文件”“删除这些 ID”授权对应配置操作，不自动授权改日志。明确一次授权多个阶段时直接完成相应阶段，不重复请求许可。单纯生成草稿后直接交付，不额外追问是否插入。

提交 Git、推送、版本文件改名只在用户指令涵盖时执行。一次具体 ID 的删除指令不成为今后其他门派的默认删除规则。

## 1. 找技改，建立确定操作清单

- 定位工作仓库。此项目常用路径为 `D:/Code/LiyuTargetMon`；以当前目录和用户指定路径为准。读取适用的 `AGENTS.md`、Git 状态、目标门派现有条目及类别／门派注释，保留用户未提交内容。
- 研究前读取 [证据与数据源](references/evidence.md)。找到旗舰版正式公告、目标日期之后的补充调整，并对照前后版本；公告列出整张奇穴表，不代表每项都改了。
- 先筛选心法范围，再判断 PvP 适用性。T 心法专属效果默认过滤，共享技能按非T或通用来源核验。仅对非侠士、NPC或首领生效的效果，以及仅由命中或击杀这些目标触发的增益，直接过滤。按本项目的 PvP 筛选约定，奇穴效果明确包含无双或无双等级加成时，整项按 PvE 过滤，即使同时提供会心、会效等强化也一并筛除。用户说明、效果表格、待处理和待截图清单均只展示通过上述筛选的分支，再进行强化范围分类与数值判断。详细边界见 [配置格式与仓库规则](references/configuration.md)。
- 对候选状态记录门派／心法、来源类型及触发链、旧／新效果、BuffID:Level、IconID、正负面、现有分类与位置、证据及配置操作。来源类型按直接赋予效果的机制标注为“心法自带”“技能本体”“秘籍”“奇穴”等，有叠加修饰时分别说明基础来源和修饰来源。
- 展示需要监控的效果时，采用“心法｜技能／奇穴来源｜需要监控的效果”三列表格，示例见 [证据与数据源](references/evidence.md)。心法列单独填写“通用”“云裳”“花间”“离经”等心法称呼。来源列显式标明来源类型及具体名称，例如“【技能本体】酒中仙 → 昊破”“【秘籍】恶狗拦路”。秘籍效果写明对应秘籍名称，奇穴修饰及重数写入效果栏。
- 奇穴修饰及其重数写入“需要监控的效果”栏，与对应效果放在一起，例如“第二重「拂罗」修饰后提高至65%”。条目草稿的来源说明也需包含已核实的奇穴名称与重数。按对应版本的官方公告或奇穴表核对，混选标注“混选奇穴”，未知重数标注“重数待核”，已移除来源可注明“旧版第几重奇穴”。分析 JSON 记录来源类型及适用的心法、触发技能、秘籍名称、奇穴名称和重数，尚未核实的信息标注待核。
- 将“效果发生变化”“数字 ID 已核实”“配置确需修改”分别判断。技能或奇穴 ID 不是 BuffID；同名、同图标也不代表同一条状态。
- 先按强化范围确定增伤状态的分类。**“爆发”用于通用强化**。单个招式、下一次特定招式施展或限定套路的强化，单独评估监控价值，个别需要跟踪时归入“其他”。分类与收录依据见 [配置格式与仓库规则](references/configuration.md)。
- 分析候选时，完成分类后按默认阈值筛选数值。减伤或已归入爆发的通用强化按该状态**可达到的有效总数值**判断，可叠层时计入叠层效果，总数值 **≤15%** 时筛除，**>15%** 时纳入候选。记录单层数值、最大层数和叠加规则。化解数值 **<10% 且不能叠层** 时筛除。化解恰好10%，以及低于10%但能够叠层的状态，继续进入候选核验。数值或叠层能力待确认时记录待核，详细规则见 [配置格式与仓库规则](references/configuration.md)。
- 交付优先列确定的新增／修改／删除。来源排查和未改动的保留项单独标识；用户只要确定项时不把它们混入清单。
- 奇穴移除、重做不自动证明所有关联 BuffID 废弃。只有已确认的对应关系及退役依据，或用户明确指定删除，才列入可执行删除；注明后者是用户指定操作。
- 若仅变化为伤害数值、触发条件或持续时间，而现有监控字段无需变化，不制造“修改配置”任务。没有确认的修改项就写“暂无”。

## 2. 核对数据库或截图

- 查数据库时核实版本、端、更新时间／快照日期及实际查询结果，记录来源链接。旧库可以辅助识别旧 ID，不能用来声称新版本已验证。
- 截图读取名称、效果说明、`ID`、`Level`、`IconID`；保留原始图像作为证据。剩余时间不等于总持续时间。图标编号以调试 `IconID` 为准。
- 列出“仍需截图核实”的状态时，每项同时提供来源类型、可执行的复现路径、观察对象、Buff 简要效果及具体待核字段。复现路径写清必要的心法、奇穴重数／核心前置或秘籍、技能操作顺序和截图时机，详见 [待截图清单与复现路径](references/evidence.md#待截图清单与复现路径)。收到截图后更新已核状态和待核字段。
- 对用户指定加入草稿的条目，用户直接粘贴完整调试字段时也可据此生成草稿，来源注明“用户提供的调试文本”；不要求重复补图，也不称为已独立核验截图或数据库。
- 数据库与当前截图冲突时保留差异，以可识别版本的游戏实测证据为优先；不要无提示覆盖已有映射。模糊数字或缺失等级不靠猜测补齐。
- 缺少必要数据时，先交付已完成的技改分析、确定项及缺失字段，等待后续数据库或用户截图。一次查不到不等于该状态不存在，不循环等待数据库刷新。

## 3. 生成草稿；按指令写入

生成或插入前读取 [配置格式与仓库规则](references/configuration.md)。

- **草稿收录由用户明确指定决定，用户指定加入优先于默认数值筛选阈值。** 按用户明确点名加入的名称、ID 或已确认加入的清单处理，低于默认阈值的指定条目也按指令收录。用户未指定加入的条目默认忽略，包括已通过阈值或已查到 BuffID 和 IconID 的条目。数据库结果用于核验所指定条目的字段。
- 在系统临时目录保存草稿和数据出处，给出用户可直接检查的条目；在插入指令前不改生产配置。
- 用户说“JSON”但给定格式是 `szNote = ...` 时，按其示例输出 `.jx3dat` 的 Lua table 片段；要求严格 JSON 时输出合法 JSON。需要两种时分别提供，不能把 Lua 称为严格 JSON。
- 对用户已指定加入的条目，确认 BuffID／图标及效果后生成草稿。证据中如实记录数据库或截图的实际 `Level`，未知字段标记待核。
- **新增 Buff／Debuff 的草稿和配置默认使用 `nLevel = 0`，表示不限等级匹配。** 个别需要指定非零等级的条目，先列出名称、BuffID、建议等级及理由，交由用户确认后采用。用户已明确指定的配置等级按其指令处理，详细约定见 [字段约定](references/configuration.md#字段约定)。
- 归入“其他”类别的 Buff／Debuff，默认使用状态名称作为别名，即 `szContent = szNote`。“标记”等特殊别名按用户指定或该状态已确认的特殊规则设置。
- 收到配置指令后，先定位“类别 → 门派”段、相邻条目及下个门派注释。修改在原条目位置覆盖，新增追加到该类别下该门派段的末尾，位于下一个门派注释之前。同批新增按确认顺序排列，缺少门派段时按现有门派顺序建立注释段。
- 实际文件操作严格依次执行“Buff／Debuff → 四行模式 → AllBuff → 两行模式”。先完成适用的 `BuffPriorityLevel`、`DebuffPriorityLevel`，再同步四行模式对应容器。随后独立处理 `AllBuffPriorityLevel`，再同步两行模式对应容器。删除也按此顺序执行。
- 四行模式的 TARGET／CLIENT_PLAYER 正面容器对应 Buff 表，负面容器对应 Debuff 表。两行模式的两个混合容器对应 All 表。“相同位置”按对应源表的类别、门派段和相邻条目顺序确定。All 的位置与特殊处理独立核对，保留各容器的字段顺序、颜色和边框。重复执行时先核对已存在条目。
- 进行条目级编辑并保留编码和换行。删除用 `dwID + nLevel` 定位，不按名称全局替换；检查同 ID 的其他等级后再决定范围。
- 写入后按“Buff／Debuff ↔ 四行、All ↔ 两行”分别核对数量、分类与门派位置、ID／图标／等级、UUID、颜色、边框及原有顺序。确认差异只包含授权操作，运行适当的差异／语法检查；不需要为单纯数据编辑新增测试框架。

## 4. 按指令处理更新日志

- 读取当前 `docs/guide/change-log.md` 的目标版本及历史写法，在对应门派下记录已完成、面向用户的状态更新。保留版本日期、缩进、门派顺序及 `:::info 更新信息` 容器。
- 常规条目使用四类短句，按实际正负面填写 Buff／Debuff。采用 `修复某名称 Debuff 显示`、`修改某名称 Buff 别名为某内容`、`新增某名称 Buff`、`删除某名称 Debuff` 等写法。
- 常规条目省略 ID、等级、控制类型、两行／四行模式及具体文件位置等括号附注，这些定位细节放入临时核对记录。例如写 `修复沉醉 Debuff 显示`、`删除雷震子 Debuff`、`新增峙峰断川 Debuff`。
- 门派注释修正及单条状态的分类、排序调整放入内部维护记录。需要概括已完成的通用整理时，在“其他”下使用 `调整了部分 Buff / Debuff 的归类以及顺序`，一次版本记录一条。
- 同门派、同名称、同操作且同为 Buff 或同为 Debuff 的记录合并为一条，即使涉及多个 ID、等级或控制效果。分别存在正面与负面状态时，保留各自的 Buff、Debuff 条目。
- 特殊修复按实际需要保留关键使用条件，例如 `切换无相楼的情况下，修复单持、双持 Buff 显示`。资料片升级及通用项目归入“其他”，例如 `更新至「山海源流」资料片`，资料片名按目标版本填写。
- 日志内容以实际完成的配置工作为依据。待核状态、技改研究结论及待执行候选保存在临时分析记录。用户只要求精简已有日志时，围绕指定版本的现有条目调整措辞和归并。
- 提交前核对条目重复、括号定位细节和内部维护条目。按用户要求暂存相应范围，使用给定 commit 文案，提交后报告短哈希和工作区状态。提交指令不等于推送指令。
